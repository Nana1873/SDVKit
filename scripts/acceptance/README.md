# Live acceptance scripts

Each script runs one SDVKit workflow end to end against the real game: build, package, start a review, act through SDVKit's tools, read the effect back, stop and reset. It stops at the first unmet check, always cleans up, and leaves its evidence below the lab root.

| Script | Proves | Extra input | Guide |
| --- | --- | --- | --- |

| [`crop-machine.ps1`](crop-machine.ps1) | A wrong Content Patcher Keg rule yields Wine; the correct rule turns a natively watered and harvested Strawberry into two Joja Cola, refuses stale or unfaced actions, and the Cola survive a chest transfer, a save and a restart. | `-ContentPatcher` (2.9.1 folder) | [Test a machine rule](../../docs/test-a-machine-rule.md) |
| [`player-actions.ps1`](player-actions.ps1) | Walking in four directions and walking versus running; `stardew_world_move` (exactly one tile in each direction with the reported tile confirmed by a runtime read, a turn without a tile change, and a blocked target refused with `worldMoveTargetBlocked`); `lab_warp` and a location change through a map warp; hotbar number keys and the wheel refusal; game menu open, inventory move by two clicks, tab click and Escape; hoe, pickaxe and scythe on the faced tile; `stardew_world_act` (hoe by `useTool`, the Farm sign by `check`, refusal of a far tile); `stardew_fixture_item_add` and placing the added chest by `check`; `stardew_fixture_npc_place`, the runtime NPC list, talking to Lewis and giving him a gift (friendship rises each time); `stardew_world_interact` watering a planted plot; `stardew_container_transfer` both ways through a placed chest; fishing preparation and cast. ## Run a script

Requirements: PowerShell 7.3 or later, one ready game and SMAPI installation (`sdvkit doctor`), a built or extracted `sdvkit.exe`, and the extra inputs above. The sample mods come from `docs/examples/`.

```powershell
pwsh scripts/acceptance/shop.ps1 -SdvKit .\src\SdvKit.Cli\bin\Release\net8.0\sdvkit.exe -GamePath 'D:\Games\Stardew Valley' -LabRoot D:\Labs\acceptance
```

- `-LabRoot` is the lab every live command runs from. Use a dedicated folder with a short path; Windows limits path length below it. The scripts can share one lab root; run one at a time.
- It refuses a lab root that is, or is inside, the game folder or the normal Stardew data folder. Before starting, it requires both topologies to be stopped with nothing retained. It stops and resets only a review whose target lies in its own evidence folder, also when a start fails or the run fails between a stop and a planned restart. Like any `project review status` call, the preflight finalizes a review whose game has already exited. The lab root check compares paths as written and does not resolve junctions.
- It records a listing of the game folder's top level, the game's `Mods` folder and the normal Stardew data folder (saves, settings, logs) before and after, and fails when they differ. A listing compares names, sizes and write times; it does not hash files, and it does not cover a mod manager's own folders. Your own changes during the run count too. `-SkipProtectedCheck` turns this off.
- Exit code `0` means every check passed; `1` means a check failed or cleanup did not complete. The console names the failed check.
- The lab starts the game window without giving it focus, so you can keep using other windows during a run. Clicking into or switching to the game window while a script sends input (also when Windows activates it after you close or minimize the window in front) makes SDVKit report `inputForegroundChanged`: the input may have run, so the run stops as inconclusive. Leave the game window alone during a run, and rerun after such a stop.
- While developing SDVKit, `player-actions.ps1 -Only npc,item` runs the shared setup and then only the named sections (`walk`, `move`, `mapwarp`, `hotbar`, `menu`, `tools`, `act`, `interact`, `item`, `transfer`, `npc`, `fishing`), always in that order. Its evidence goes to `player-actions-partial`. A partial run is never acceptance evidence: PRs and releases need a full run.
- `player-actions.ps1 -Topology network-2 -Role farmhand` (or `-Role host`) starts a `network-2` review on the test-save baseline and runs `walk`, `move`, `hotbar`, `menu`, `act`, `interact` and `transfer` through that role ([#297](https://github.com/Nana1873/SDVKit/issues/297)). In a farmhand run the host does the world-changing setup (tilling and planting the plot, placing and filling the chest), because the farmhand has no such fixture tools. `-Screen <id>` (1 or higher; screen 0 is the host) starts the single test-save review, opts it into split-screen and runs `walk`, `move`, `hotbar` and `menu` on that screen from the local farmhand's cabin bed, plus `act` and `interact` as refusals: Stardew forces gamepad mode there, so `stardew_world_act` returns `worldActionCursorAimUnavailable`, and the cabin floor has no soil to water. `mapwarp`, `tools`, `item`, `npc` and `fishing` need map reads or fixture tools and are skipped with a console note. Every tool call and every menu, inventory and world read carries the `--role` or `--screen` selection; every runtime read asserts the selected role or screen, and inventory reads assert that player's ID. Such a run is not full acceptance and complements the full single run. Evidence goes to `player-actions-farmhand`, `player-actions-host` or `player-actions-screen<id>` (with `-Only`: `player-actions-partial-<mode>`). The topology the run started (`network-2` for a role, `single` for a screen) is stopped and reset at the end, also after a failure. A `network-2` start that fails with `gameSideStale` ([#325](https://github.com/Nana1873/SDVKit/issues/325)) stops and resets its host and can simply be rerun.
- Evidence goes to `<lab-root>/.sdvkit/acceptance/<script>/<timestamp>/`: `identity.json` (sdvkit version and SHA-256, game and SMAPI versions) and provider hashes, every SDVKit result as numbered JSON, screenshots, and the protected-folder listings.

The GMCM scripts click fixed screen positions, because GMCM's page exposes no menu components. They were measured for GMCM 1.16.0 in the default 1280x720 lab window, and the script refuses to click in another viewport. For other sizes, measure the checkbox, the slider and the Save button on the screenshots and pass `-CheckboxX`, `-CheckboxY`, `-SliderMinX`, `-SliderMidX`, `-SliderMaxX`, `-SliderY`, `-SliderMaxDragX`, `-SaveX` and `-SaveY`. The checks prove that no move changes the value before Save and that the final drag reaches the maximum; the intermediate Row 17 is visible only on the screenshots. For the checkbox, the value and the staged config stay `false` after the click, and a saved `true` followed by the warp after the restart proves that the click landed on the checkbox.

## Shared helpers

[`SdvKitAcceptance.psm1`](SdvKitAcceptance.psm1) holds the shared steps: run sdvkit and keep its output, call a tool, wait for a ready review, click a menu component by its bounds, take a screenshot, stop and reset, and compare the protected folders. For GMCM and mod log checks it also copies the GMCM provider (`Copy-GmcmProvider`), starts a review with a companion (`Start-CompanionReview`), clicks Save and accepts the change with `config-reconcile` (`Save-GmcmPage`), runs a mod console command and reads its log line (`Invoke-ModLogCommand`, `Get-SmapiLogPath`), and reads the player position (`Get-PlayerPosition`). Write a new script for another workflow with these helpers, and add it to the table above and to the [release procedure](../../docs/releasing.md#run-the-selected-live-checks).
